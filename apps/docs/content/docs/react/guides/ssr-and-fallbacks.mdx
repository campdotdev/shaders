# SSR and fallbacks

Matter is fundamentally a client runtime — it needs `navigator.gpu`, which doesn't exist on the server. This page covers the patterns for using Matter in Next.js (or any SSR framework) and handling browsers that don't support WebGPU at all.

## The core constraint

`three/webgpu` references `self` and `navigator` at module load time. Importing it in a server bundle (RSC, getServerSideProps, etc.) throws. So:

- Matter components are always client components.
- Pages that import them either need `'use client'` themselves, or they need to load Matter via `next/dynamic` with SSR disabled.

That applies to anything reaching the renderer. It does not apply to every export both packages have, which is what the subpaths below are for.

## The three-free subpaths

Some of what Matter ships is plain arithmetic that never touches the GPU: parsing a color string, converting between OKLCH and linear sRGB, asking whether a display can show a color. Those reach `three/webgpu` only because the root entry re-exports the renderer alongside them, so each has a second entry point that doesn't.

| Import from | Instead of | For |
| --- | --- | --- |
| `@lovo/matter/color` | `@lovo/matter` | `parseColorString`, the OKLab/OKLCH conversions, the gamut helpers, the sRGB transfer functions |
| `@lovo/matter-react/gamut` | `@lovo/matter-react` | `useDisplayGamut` |
| `@lovo/matter-react/poster` | `@lovo/matter-react` | `<ShaderPoster>` |

```tsx
// Server-renders fine — no path to three.
import { parseColorString, linearSrgbToOklch } from '@lovo/matter/color'

export default function Swatch({ color }: { color: string }) {
  const [lightness] = linearSrgbToOklch(...parseColorString(color))

  return <span data-dark={lightness < 0.5}>{color}</span>
}
```

The functions are the same ones the root entry exports; the only difference is what comes along with the import. So this is not a reduced or "lite" build — reach for the subpath whenever you need only the scalar half, and keep `ssr: false` for anything that renders a scene.

<Callout>
  Each subpath is covered by a test that imports it with no DOM present. `three/webgpu` reads `self` at module load, so if three ever creeps back into one of these graphs the import throws and the test fails, rather than the breakage surfacing as a crashed server render.
</Callout>

## Next.js — the dynamic import pattern

```tsx
import dynamic from 'next/dynamic'

const Hero = dynamic(() => import('./hero'), { ssr: false })

export default function Page() {
  return <Hero />
}
```

`Hero` is a regular client component that imports `@lovo/matter-react` and the registry component. The page itself can stay an RSC.

## Webpack alias for three (Next 14+)

Three ships two standalone bundles — `three.module.js` (core only) and `three.webgpu.js` (core + WebGPU + TSL). If both end up in your bundle, you get the dreaded `Cannot read properties of undefined (reading 'usedTimes')` error on dispose.

Add this to `next.config.ts`:

```ts
import { resolve } from 'node:path'
import { createRequire } from 'node:module'

const require = createRequire(import.meta.url)
const threeMain = require.resolve('three')
const threeDir = resolve(threeMain, '..', '..')

export default {
  webpack(config) {
    const webgpuBundle = resolve(threeDir, 'build/three.webgpu.js')
    config.resolve.alias = {
      ...config.resolve.alias,
      three$: webgpuBundle,
      'three/webgpu$': webgpuBundle,
      'three/tsl$': webgpuBundle,
    }
    return config
  },
}
```

This forces every `three` import to resolve to the unified bundle. Same idea applies to Vite, Webpack, and Rspack — see your bundler's resolve-alias docs.

## Fallback for browsers without WebGPU

Some browsers (Firefox stable, Safari < 18, older Chrome) don't ship WebGPU yet. Wrap any Matter subtree in `<FallbackBoundary>`:

```tsx
import { FallbackBoundary, ShaderScene } from '@lovo/matter-react'
import { Aurora } from '@/components/matter/aurora'

export function Hero() {
  return (
    <FallbackBoundary fallback={<img src="/hero-fallback.png" alt="" />}>
      <ShaderScene style={{ height: '60vh' }}>
        <Aurora />
      </ShaderScene>
    </FallbackBoundary>
  )
}
```

When `navigator.gpu` is missing or `requestAdapter()` returns `null`, the fallback renders. Use any React node — a static image, a CSS gradient, an `<svg>`, a "your browser doesn't support WebGPU" message.

<Callout>
  Don't try to detect WebGPU yourself with a conditional render. Detection is async (`requestAdapter` is a Promise), and doing it client-side causes hydration mismatches. Let `<FallbackBoundary>` handle it — it renders the fallback during the same render pass and swaps in the real scene only after the device is ready.
</Callout>

## When renderer init fails

`<ShaderScene>` tries WebGPU, then falls back to WebGL2 automatically. If neither is available, init fails. A bare `<ShaderScene>` then renders nothing — a transparent canvas. It never shows a raw error to users.

To show something in its place, wrap it in `<ShaderPoster>`: the poster stays up because the scene never signals its first paint. To report the failure to your own telemetry, pass `onError`:

```tsx
<ShaderScene onError={(error) => reportToSentry(error)}>
  <Aurora />
</ShaderScene>
```

`onError` receives a `MatterError` with `code: 'renderer-init'`; the original thrown error is on `.cause`. This is separate from `<FallbackBoundary>`, which covers SSR and hydration — not renderer failure.

## What gets server-rendered

If you wrap a scene in `next/dynamic` with `ssr: false`, nothing from that subtree ships in the server HTML — which is right, because a canvas has nothing useful to say before it has a GPU. The fallback inside `<FallbackBoundary>` is what users see during hydration and on unsupported browsers.

The subpaths are the exception, and worth remembering when you reach for `ssr: false` reflexively. A page that reads colors with `@lovo/matter/color`, or checks the display gamut with `@lovo/matter-react/gamut`, or shows a `<ShaderPoster>` while the scene loads, renders all of that on the server normally. Only the scene itself has to wait.

If you have SEO-critical content that's currently hidden behind a Matter component, lift it out into the surrounding RSC. Matter is for decoration; the surrounding page is for content.
