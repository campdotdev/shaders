# Three / r3f

Shaders has two rendering modes:

- **Mode 1: Shaders-managed scene.** `<ShaderScene>` owns the canvas. Tier 1 components (`<Aurora>`, `<LinearGradient>`, etc.) only work in Mode 1. This is what [Get Started](/getting-started) covers.
- **Mode 2: Bring your own Canvas.** You already have an `@react-three/fiber` `<Canvas>` for a 3D scene, and you want Shaders' TSL primitives in a material. This page is for Mode 2.

Mode 2 doesn't auto-detect r3f — it's an explicit opt-in via the `useShaderMaterial` hook.

## The escape hatch — `useShaderMaterial`

`useShaderMaterial` takes a function that builds a TSL color expression and returns a Three.js material you can drop onto any mesh:

```tsx
import { Canvas } from '@react-three/fiber'
import { fractalNoise, useShaderMaterial } from '@camp-dev/shaders'
import { mix, uv, vec3 } from 'three/tsl'

// Hoisted so its reference is stable: useShaderMaterial rebuilds the material
// whenever the builder changes, so an inline arrow would recompile every render.
const buildColor = () => mix(vec3(0.1, 0.2, 0.6), vec3(0.8, 0.6, 0.2), fractalNoise(uv()))

function ShaderPlane() {
  const material = useShaderMaterial(buildColor)
  return (
    <mesh material={material}>
      <planeGeometry args={[2, 2]} />
    </mesh>
  )
}

export function Scene() {
  return (
    <Canvas>
      <ShaderPlane />
      {/* your other r3f content */}
    </Canvas>
  )
}
```

The material plays by r3f's rules — dispose, frameloop, demand-rendering all work as r3f expects. Shaders just provides the TSL math; r3f provides the scene graph.

## Draw strands in your scene

Strands are fine curves of light drawn as a mesh, so they sit in your 3D scene: your camera moves around them, and your meshes hide the ones behind them. A strand stays the same number of CSS pixels thick at any distance.

For strands, the builder returns two nodes. `vertex` places each vertex, and `color` shades each pixel:

```tsx
import { useEffect, useMemo } from 'react'
import {
  createStrandGeometry,
  extrudeStrand,
  strandProfile,
  useShaderMaterial,
} from '@camp-dev/shaders'
import { mix, sin, vec3 } from 'three/tsl'

const STRAND_WIDTH = 3

const buildStrands = () => {
  const strand = extrudeStrand(
    // Where a strand is: a sine wave along x. Each strand sits further back.
    (along, across) => {
      const x = mix(-3, 3, along)
      return vec3(x, sin(x.mul(4)).mul(0.15), across.mul(-6))
    },
    { strandWidth: STRAND_WIDTH },
  )
  const light = strandProfile(strand.distance, STRAND_WIDTH)

  return { color: vec3(0.12, 0.3, 0.75).mul(light), vertex: strand.position }
}

function Strands() {
  const material = useShaderMaterial(buildStrands, { blending: 'additive' })
  const geometry = useMemo(() => createStrandGeometry({ strands: 24, samples: 256 }), [])

  useEffect(() => () => geometry.dispose(), [geometry])

  return <mesh geometry={geometry} material={material} />
}
```

Four primitives do the work:

- `createStrandGeometry` builds the mesh: one strip of triangles per strand, with `samples` points along each.
- `extrudeStrand` takes your path and widens it into a strip. The path receives `along` (0 to 1 down the strand), `across` (the strand's place among the others, 0 to 1), and `seed` (a random number per strand), and returns a point in the mesh's own space. How far apart the strands sit, and how much each one strays, is up to your path.
- `strandProfile` fades each strand from its center line to its edges.
- `{ blending: 'additive' }` adds each strand's light to what is behind it, so strands brighten where they cross.

`strandWidth` is how thick one strand is, edge to edge. The bright core is about 40% of that, because the fade reaches nothing at the edge. A strand thinner than 3 CSS pixels keeps that width and dims.

The path must depend only on its inputs and on uniforms. To animate it, read a time uniform inside it.

## When to use Mode 2

- You're building a 3D scene (geometry, lights, cameras) that also wants shader-y materials.
- You need fine control over the render loop (custom frameloop, post-processing chain).
- You want to use Shaders primitives (`fractalNoise`, `voronoi`, `colorRamp`, …) without the constraints of a single full-bleed 2D quad.

## What you lose in Mode 2

- **No `<ShaderScene>` defaults.** Pause-when-offscreen, DPR clamping, the scheduler — none of that is wired up by `useShaderMaterial`. You manage r3f's lifecycle yourself (or use r3f's `frameloop="demand"`).
- **No Tier 1 components.** `<Aurora>`, `<LinearGradient>`, etc. are bound to Mode 1 and assume `<ShaderScene>` is the parent. You'd need to extract their TSL math by hand if you want it in Mode 2.
- **No `useCursor` / `useScroll` / `useResize`.** Those hooks require a `<ShaderScene>` to plumb the canvas; in Mode 2, use r3f's `useThree()` and write your own cursor/scroll wiring.

## The recommendation

Default to Mode 1. Mode 2 exists for the case where you already have an r3f scene and the alternative is duplicating shader work in two canvases. If you're not building a 3D scene, you don't need Mode 2 — `<ShaderScene>` does everything you want.

<Callout>
  Shaders and r3f can coexist on the same page in separate canvases — one `<ShaderScene>` for your hero shader, one r3f `<Canvas>` for a 3D model below it. They don't interfere. Mode 2 is only relevant when you want to *combine* them in one canvas.
</Callout>
