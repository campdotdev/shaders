<plan_listing_caveats_for_3.5>

I pre-reviewed the 3.5 plan listing for `registry/aurora.tsx`. Apply these as caveats when briefing the implementer:

**A1 — CRITICAL: displacement axis mismatch.** The plan listing has:
```tsx
const displacement = vec2(amplified.mul(intensityUniform), 0)  // x-only
const dUv = displace(uv(), displacement)
const band = (dUv.y).clamp(0, 1)  // ← uses .y!
const colorAtUv = colorRamp(band, stops)
```
Since displacement is x-only, `dUv.y == uv().y` so the displacement does NOTHING visually. Spec line 461 says "vertical band gradient" + "displace by `vec2(fbm, 0)`" — bands must be x-based. **Fix: use `dUv.x.clamp(0, 1)` instead of `dUv.y`.** This is a real bug that would ship a static-looking Aurora.

**A2 — `vec4(vec3, scalar)` overload.** Plan rebuilds the color via three `.x`/`.y`/`.z` swizzles:
```tsx
material.colorNode = vec4(colorAtUv.x, colorAtUv.y, colorAtUv.z, 1)
```
Replace with `vec4(colorAtUv, 1)` (overload verified working in DotField, Waves, MeshGradient).

**A3 — `amp.mul(1).add(1)` is a no-op cleanup.** Plan has `((amp).mul(1)).add(1)` for cursor amplification. The `.mul(1)` is redundant; just `amp.add(1)`.

**A4 — `three/webgpu` imports.** Per memory: single combined `import { Mesh, MeshBasicNodeMaterial, PlaneGeometry, Vector2 } from 'three/webgpu'`. Plan listing splits between `'three'` and `'three/webgpu'`.

**A5 — Cursor canvas-rect normalization is centralized.** `useCursor()` with no args — no element plumbing. Centralized fix from 3.2.

**A6 — Initial `cursorVec`.** Use `Vector2(0.5, 0.5)` (centered). No `resVec` needed for Aurora — it doesn't use `useResize`.
</plan_listing_caveats_for_3.5>
